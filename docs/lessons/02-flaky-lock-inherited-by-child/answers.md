# 第 9 節解答

**1.** `flock` 的鎖屬於「那一次開啟檔案」，fork 會讓子程序得到指向同一次開啟的把手副本。父程序關掉的只是自己的那一個，
副本還在，所以鎖還在。若改用 POSIX `fcntl` 記錄鎖，鎖屬於 process，子程序不會繼承，父程序重開時就拿得到；
代價是同一個 process 內關掉任何一個指向該檔案的把手，鎖就消失。

**2.** 需要兩個條件同時成立：這個測試正持有鎖，而另一個 thread 剛好在 fork 子程序。單獨跑時沒有別的 thread 在 fork，第二個條件不會成立。

**3.** `CLOEXEC` 是在 exec 的那一刻才關閉把手。fork 與 exec 之間，子程序確實握有副本，時間窗就在這裡。

**4.** 例如：(a) 修改正式程式來遷就只存在於測試的情況；(b) 真的有兩個程式在搶同一個目錄時，第二個要晚一秒才被拒絕，
而且如果第一個剛好在那一秒內結束，第二個就會接手——原本的設計是「立刻、明確地拒絕」；(c) 一秒只是猜的，時間窗更長時仍會失敗，問題被藏起來而非解決。

**5.** 舊測試在子程序被終止後只開啟一次 WAL，開完就檢查、結束，沒有「關掉後立刻重開」。
時間窗只會影響「我剛關掉、又馬上要拿回鎖」的那一刻；新測試為了確認「第二次重啟結果相同」多了這個動作。

**練習：實際結果（2026-11-13，WSL2，各 20 次）**

| `time.sleep(...)` | re-lock 失敗 |
|---|---:|
| 1.0 | 20/20 |
| 0.1 | 20/20 |
| 0.01 | 20/20 |
| 0 | 20/20 |

連 0 秒都每次失敗。寫這份解答時我原本預測「0 秒多半成功」，實際跑過才發現錯了：
Python 的子程序在 fork 之後還要執行 `time.sleep(0)`、準備 `os.execv` 的參數，這些都是直譯器裡的程式碼，
要花上毫秒等級的時間；而父程序只是關一個把手、開一個檔案、呼叫一次 `flock`，快得多。所以時間窗永遠大於父程序需要的時間。

真正的測試用的是 Rust 的 `Command::spawn`，在 Linux 上走 `posix_spawn`，子程序幾乎一建立就 exec，時間窗短得多，
只有在父程序剛好也在那一瞬間關檔重開時才會撞上——這就是為什麼它是「偶爾」失敗。這個對照也說明了一件事：
把時間窗放大（Python 示範）是為了證明原因，不代表真實情況的頻率。
