# 第 9 節解答

**1.** 對工作區內的 crate，cargo 計算 `-C metadata` 雜湊時不使用它在磁碟上的絕對路徑（第 3 節第 4 步實測兩份複本的雜湊都是 `2ef2aa09102a885f`），
所以兩份複本的編譯結果在共用的建置目錄裡是同一組檔案。cargo 接著只看原始碼的修改時間是否比上次編譯新；複本保留了舊時間，於是被判定為 `Fresh`。

**2.** 見練習的實測：若乾淨的複本是在 `mutant` 編譯之後才建立、檔案時間較新，cargo 會判定原始碼比既有結果新，重新編譯（`Compiling raft-protocol`），測試通過。
這正是第 6 節「不保留修改時間」做法的原理，也說明它依賴時間順序。

**3.** 植入後失敗，只有在「不植入就會通過」的前提下才有意義。若某個測試本來就會失敗（環境問題、偶發失敗、或像這次的建置污染），植入後失敗並不能說明它擋得住植入的錯誤。
先跑對照組，才能把失敗歸因於植入的錯誤；對照組在植入任何錯誤之前跑，也確保它不會被任何一個案例污染。

**4.** 因為它的「預設」方向是不安全的：取不到值時代表「全部確認」。現在固定三台節點，`acks` 永遠有兩個元素，這個分支不會執行；
但 S4 讓節點數可以改變之後，只要 follower 數少於需要的數目，leader 就會在沒有多數確認的情況下回覆讀取。不確定時應該選擇「沒有確認」，這和儲存層「不確定就拒絕啟動」是同一個原則。

**5.** 不能。污染讓結論在兩個方向都不可靠：那個測試可能是被前面案例的錯誤弄失敗的（所以「抓到」不能證明它有效），但它也可能本來就有效。
唯一的辦法是在隔離的環境下重跑。

**練習：實際結果（2026-11-13）**

先用共用建置目錄編譯並執行 `mutant`（`QUORUM = 3`），之後才建立一份乾淨的複本（不保留舊的修改時間），再用同一個共用建置目錄執行：

```text
exit=0
Compiling raft-protocol
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 3 filtered out; finished in 0.00s
```

cargo 重新編譯，測試通過。原因是這份複本的檔案時間比 `mutant` 留下的編譯結果新。

但如果複本是在 `mutant` 編譯**之前**就建立好的（例如一次把所有案例都先複製完，再依序編譯），它的檔案時間就比 `mutant` 的結果舊，cargo 又會判定 `Fresh`。
開發時的第一次實驗正是這樣：三份複本先全部建好，第三份即使沒有保留舊時間，也被判定為 `Fresh`。
所以「不保留修改時間」只在「複製緊接著編譯」時有效；獨立的建置目錄則不論順序都正確。
