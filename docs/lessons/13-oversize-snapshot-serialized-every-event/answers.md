# 第 9 節解答

**1.** 它只控制 `snapshot_too_large` 這一行 trace 要不要再印一次。序列化在那個 `if` 的外面、而且在它前面，每次都會執行。
它讓 bug 更難看出來，是因為名字和位置都像在說「這個情況已經被記住並處理了」；輸出也配合這個印象：trace 只出現一次，看 log 的人會以為節點只試了一次。

**2.** 「到期」看的是 WAL 的大小（或上次快照以來套用的筆數）。這兩個數字只有在快照安裝成功、WAL 被改寫之後才會變小。
放棄的時候什麼都沒有安裝，WAL 還在繼續變長，所以條件只會越來越成立。

**3.** 固定每 1,000 筆：大約 1,000 次。加倍：第一次放棄之後，間隔是 1、2、4、8……筆數加倍 20 次就超過 100 萬（2 的 20 次方約 105 萬），所以大約 20 次。
每一次都是一次完整的序列化（重現時約 50 毫秒），差別是 50 秒對 1 秒。這是推算，沒有實際跑 100 萬筆。

**4.** 上限從寫死的常數改成 actor 的欄位 `snapshot_limit`，正式程式設為 64 MiB，測試設為 64 bytes，十筆小資料就超過了。
這個 bug 是邏輯錯誤（放棄之後沒有記住），和上限是多少無關，所以小上限能走到同一條路徑。
漏掉的是成本：小資料的序列化不花時間，測試只能數「試了幾次」，量不出「每次多慢」；那一部分由第 3 節用真的 64 MiB 量。
另外，測試直接呼叫 `maybe_compact`，沒有經過真實的事件迴圈。

**5.** 對得上的：超過上限時不會安裝快照（「停止壓縮」），而且會印一行 trace（「並記錄」），log 也確實繼續成長。
對不上的：「停止」讓人以為節點不再為壓縮花力氣，實際上它每個事件都在花，只是每次都放棄。規格描述的是結果，沒有描述代價；程式滿足了結果，代價沒有人檢查。
