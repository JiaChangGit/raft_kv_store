# 第 9 節解答

**1.** libtest 執行測試時會把 `print!`／`println!` 這些巨集的輸出導向一個暫存區，只在測試失敗時一起印出。
節點的 trace 是 `io::stdout().lock()` 加 `writeln!`，直接寫到程序的標準輸出，不經過那個攔截機制，所以會和 libtest 自己的輸出搶同一個出口。

**2.** 驗收要的是「有證據證明測試擋得住這個錯誤」。編譯失敗代表沒有任何證據；判為抓到會讓沒證據的情況通過驗收，判為存活至少會讓驗收停下來。
另外標成 `build_error`，是為了讓人一眼看出該修的是植入錯誤本身（它跟不上程式的變動），而不是去加強那個測試。

**3.** 不是靠 panic 失敗的測試，例如回傳 `Result` 的測試回傳了 `Err`：libtest 會把它記為失敗，但不會有 `panicked at` 訊息。
本專案目前的測試都用斷言（會 panic），所以這是推論，沒有實際的反例；結果行與失敗清單這兩種訊號涵蓋這種情況。

**4.** 每個案例都要複製程式、編譯、執行，前面的案例可能已經花了好幾分鐘。錨點檢查只是讀檔與計數，不到一秒。
先全部檢查，錨點有問題時立刻停下，不會白跑；也能一次列出所有失效的錨點，而不是修一個才發現下一個。

**5.** 不一定。「抓到」只代表指定的測試在植入錯誤後失敗了，可能是因為別的原因（例如同時發生的偶發失敗）。
要更確定，可以比對失敗訊息是否指向植入的那條規則，或在沒有植入時再跑一次確認它會通過。本專案目前只做到前者的一部分（要求是指定的測試失敗）。

**練習：實際結果（2026-11-13）**

```text
cargo exit=0
running 0 tests
test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 9 filtered out; finished in 0.00s
old rule: SURVIVED
new rule: test_not_run
```

cargo 以 0 結束：名稱過濾不到任何測試，所以「0 個通過、0 個失敗」，對 cargo 來說是成功。
舊規則看不到 `名稱 ... FAILED`，判為「存活」，好像這個測試擋不住錯誤；新規則看到輸出中完全沒有 `test 名稱 ... ` 這一行，判為 `test_not_run`，
指出問題在案例設定（名稱打錯），而不是測試本身。這個情況是寫練習時才想到的，`test_not_run` 也是那時才加上的。
