# Bug 教學

開發這個專案時實際遇到的 bug，每一個寫成一篇可以照著做的教學。
這些 bug 都是真的：有重現步驟、有當時的輸出、有修正前後的程式。

## 給第一次讀的人

只讀三篇的話，照這個順序：

1. [WAL 長度欄位毀損](01-wal-length-corruption/README.md)：一個壞掉的數字，讓節點忘記自己投過的票。從磁碟、checksum 這些看得到的東西開始，最容易進入。
2. [剛選出的 leader 把早就 commit 的設定當成「進行中」](08-judged-before-the-term-commit/README.md)：新 leader 還不知道哪些 entry 已 commit，就先判斷有沒有進行中的成員變更，於是每次換 leader 後，成員變更都被誤拒。先讀[帶讀](../LEARNING_GUIDE.md)的寫入流程。
3. [放寬了上限，卻沒有測試守著它](18-a-limit-nobody-tested/README.md)：所有測試都通過，系統卻有一種情況永遠卡住；看「測試通過」和「功能正確」差在哪裡。

## 依 bug 的種類

21 篇都是草稿：還沒有人照各篇的「親手重現」（每篇的第 3 節）實際做過一遍。「出處」是發現這個 bug 的階段或審查；S10 是最後一次複查（2026-11-17）。
每篇的重現腳本在 2026-11-17 都重新跑過一次，結論和保存的輸出相同（`bash scripts/run_lesson_repros.sh`）。

## 怎麼發現、怎麼找到根因

同一個 bug，「怎麼被看見」和「怎麼確定原因」往往是兩件事。下表從各篇第 10 節整理：

| 編號 | 怎麼發現 | 找到根因的關鍵一步 |
|---|---|---|
| 01 | 審查回復程式，再實際改壞一個位元組 | 問「這個長度欄位被驗證之前，有沒有被拿來做決定」：截斷發生在檢查碼之前 |
| 02 | 新測試第一次和其他測試一起跑才失敗 | 單獨跑都過，只有並行時失敗：查到鎖跟著 fork 出的子程序走 |
| 03 | 做完壓縮後跑模擬器，leader 停住 | 找出 leader 想送的 entry 已被壓縮掉，而當時還沒有 InstallSnapshot |
| 04 | mutation 測試報告兩個「存活」 | 打開那兩個案例的原始輸出：測試其實失敗了，是工具讀錯 |
| 05 | 完整驗收中出現一次失敗 | 比對失敗時讀到的內容（空字串）與檔案的建立順序：看到檔案時內容還沒寫 |
| 06 | 30 個 mutation 案例有 28 個報編譯失敗 | 看 cargo 的 `Fresh`／`Compiling`：兩份複本共用了同一份建置結果 |
| 07 | mutation 測試報告一個「存活」 | 追測試的前提：它靠 GET 製造複製，而 S3 之後 GET 不再複製 |
| 08 | 先寫的單元測試第一次執行就失敗 | 把「還不知道」和「沒有」分開：新 leader 的 commit index 在本任期 commit 前不可信 |
| 09 | 模擬器第 28 個種子失敗 | 沿著那個種子的 trace 一步步走，看到 68 被 69 超車的那一刻 |
| 10 | mutation 測試一個案例「存活」 | 讀被植入的那段程式：改動被下一行抵銷，是等價突變 |
| 11 | 獨立審查：問「測試的設定讓哪些路徑走不到」 | 模擬器的快照分塊固定 7 bytes；改成隨機後，在兩個檔案之間終止就重現了 |
| 12 | 獨立審查：看模擬的用戶端把請求送給誰 | 它永遠送給最新的 leader，於是讀取的不變量碰不到過期的 leader |
| 13 | 獨立審查：讀「超過上限就放棄」那段 | 量單次序列化的成本，再確認放棄之後沒有任何狀態記住「先別再試」 |
| 14 | 新舊量測工具的數字對不起來 | 確認碼表裡包含了什麼：測試工具每次都重寫整份歷史檔 |
| 15 | 量基準時連線被中斷 | 看回覆內容的大小，超過 1 MiB 的訊框上限 |
| 16 | 獨立審查重跑 mutation，三次都停在同一個案例 | 每次都停在同一處，不是環境問題：孤立那個測試，限制時間與輸出再跑 |
| 17 | 一小時的驗收在最後一步失敗 | 用磁碟上的報告直接跑那一條規則，幾秒就重現 |
| 18 | 獨立審查逐一植入錯誤，一個存活 | 另寫探針：停掉 follower、寫 100 筆、再啟動，它永遠追不上 |
| 19 | 獨立審查逐條刪掉檢查規則 | 看案例「被哪一條規則拒絕」，而不是只看「被拒絕」 |
| 20 | 最後一次複查時讀讀取的路徑 | 問「沒有 follower 時，誰會呼叫回答讀取的函式」，寫一台的測試，立刻失敗 |
| 21 | 在新目錄從頭建置、跑全部測試 | 自己的目錄怎麼跑都過：差別在那個目錄裡早就有舊的資料夾 |

從這些經驗歸納出的做法：

- **先讓它能重現，而且只重現它。** 固定種子、固定 tag（`git archive <tag>` 取出舊版）、只跑一個測試，並限制時間與輸出（教學 16）。
- **分開「沒執行」和「通過」。** 工具的報告、測試的前提都可能悄悄失效（教學 04、07、10）。
- **故意改壞，看測試會不會失敗。** mutation 測試找出了教學 07、10、18、19 的問題，以及最後一次複查時 14 個沒人守著的檢查。
- **問「誰會觸發這段程式」。** 判斷寫對了，不代表它會被執行（教學 20）。
- **確認碼表裡有什麼。** 量到的時間包含了哪些步驟（教學 14）。
- **定期在乾淨的環境重建。** 只在自己的目錄跑的檢查，永遠帶著那個目錄的歷史（教學 21）。

## 怎麼讀

每篇都是同樣的十節。時間不多的話：讀第 1 節知道發生什麼事，跑第 3 節親眼看到，
再讀第 10 節看怎麼講。想真的弄懂，就照順序讀，並做第 9 節的練習。

## 寫作規則

樣板在 [TEMPLATE.md](TEMPLATE.md)。資料夾命名 `NN-簡短英文名稱`，內含：

| 檔案 | 內容 |
|---|---|
| `README.md` | 教學本文，十節齊全、順序固定 |
| `repro.sh` | 一行命令重現 bug，可重複執行，只在暫存目錄寫入；要改的程式從固定的 tag 取出，不從工作目錄（教學 06、13 曾因程式演進而失效） |
| `expected-output.txt` | `repro.sh` 實際執行的完整輸出 |
| `answers.md` | 第 9 節的解答 |
| 圖 | 以 Mermaid 圖源寫在 `README.md` 的 ```` ```mermaid ```` 區塊內，GitHub 會直接顯示；需要圖檔時再用工具渲染，不手寫 SVG |
| 其他輔助檔 | 例如只在舊版程式上執行的測試；在 `README.md` 說明用途 |

寫的時候請守住這幾點：

1. **只寫發生過的事。** 命令實際跑過，輸出取自實際結果，日期與 commit 可查。
   不確定當時的原因就寫不確定，不補編。
2. **新手讀得懂。** 每個術語第一次出現時用白話解釋並附原文；一段只講一件事；
   先講讀者會看到什麼，再講為什麼。
3. **用實際數值。** 例如寫「長度從 91 被改成 65536，檔案只有 230 bytes」，不寫「長度超出範圍」。
4. **分清楚程度。** 已執行驗證的、由程式推論的、還沒驗證的，各自標明。
5. **不誇大。** 是可用性問題就不說成資料遺失；修正擋不住的情況寫進第 8 節。
6. 草稿可以留「待補」，但狀態必須標「草稿」；標成「完成」前，`scripts/check_lessons.py` 必須通過，
   並且至少有一個人照著第 3 節實際做過一遍。

`scripts/check_lessons.py` 只檢查結構（章節、腳本、輸出檔是否存在），不判斷內容寫得好不好。
`bash scripts/run_lesson_repros.sh` 實際執行每篇的 `repro.sh`，比對輸出的 RESULT 段落和 `expected-output.txt` 是否相同（約 10 分鐘）。
