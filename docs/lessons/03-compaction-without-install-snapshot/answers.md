# 第 9 節解答

**1.** 兩種：index 已被壓縮（在 base 之前），或 index 還沒寫入（超過最後一筆）。在 `replicate` 裡，`next` 先被限制在
`1 ..= last_index + 1`，所以 `prev = next - 1` 最多等於 `last_index`，不會超過末端；剩下的可能只有「已被壓縮」。

**2.** 這條路徑需要「真的丟掉了 log」「有 follower 落後到 base 之前」「此時要複製給它」同時成立。單元測試各自驗證一個元件，
不會剛好組出這個組合；模擬器把整個叢集跑起來，並隨機讓節點 crash、讓訊息遺失，落後的 follower 很快就會出現。

**3.** 壓縮後陣列的第 0 格不再是 index 1，而是 base 之後的第一筆。`log[prev - 1]` 會取到錯的 entry（位置偏移了 base 那麼多），
或在 `prev < base` 時越界、甚至因為減法溢位而 panic。最糟的是「取到錯的 entry 而沒有 panic」：leader 送出錯誤的 `prev_log_term`，
一致性檢查就是在比對錯的資料，可能讓 follower 接受不該接受的 entry。明確的 panic 至少會停下來。

**4.** follower 查 `term_at(7)`，因為 7 已在它的快照裡而得到 `None`，回覆失敗。leader 收到失敗就把 `next` 往前退，
下一次送 `prev = 6`、`5`……全都在 follower 的快照裡，全都失敗。leader 永遠送不出 follower 能接受的 AppendEntries，這台 follower 就一直停在原地。

**5.** 規則沒錯，錯在把「本機壓縮」和「InstallSnapshot」切成兩步。前者單獨存在時，系統處於一個「一定會出事」的狀態，
不可能讓所有測試通過。正確的切分應該讓每一步單獨存在時都是一個完整、可運作的系統；這次的做法是把兩步合併成一個 commit，並在紀錄中寫明原因。

**練習：實際結果（2026-11-13）**

在副本中改掉 §9.4 的條件後：

- `cargo test -p raft-core append_entries_that_start_before_the_base` 失敗：斷言預期 `(true, 7)`，實際得到 `(false, 0)`——
  follower 拒絕了一個合法的 AppendEntries。
- 60 個種子、每種子 3,000 個事件的模擬：**60/60 通過**，沒有任何不變量被違反；快照共做了 3,423 次、透過 InstallSnapshot 安裝 525 次
  （未修改的版本是 3,420 次與 524 次，代表執行過程確實不同）。

為什麼模擬器沒抓到？模擬器檢查的是**安全性**不變量（同一任期不會有兩位 leader、已 commit 的資料不會改變等），不檢查**活性**
（落後的節點最後一定追得上）。以下是推論，沒有逐一驗證：follower 拒絕後，leader 會一直往前退；退到 leader 自己的 base 之前時，
它就改送快照，有時能因此繞過問題，所以多了一次安裝。但這條繞路不一定總是走得通，而模擬器也不會因為某台節點追不上而回報失敗。

結論：§9.4 的缺口只靠模擬器不會被發現，所以它需要專門的單元測試，以及 mutation 測試 `s2_no_append_before_base_rule` 確認那個單元測試真的有效。
若要讓模擬器也能抓到，必須加上活性檢查（例如「網路恢復後，在一定的虛擬時間內每台節點都追上 commit」），這是目前沒有做的。
