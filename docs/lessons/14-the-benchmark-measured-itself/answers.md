# 第 9 節解答

**1.** 讓節點的 log 一直很短，節點自己的每筆成本就不可能隨時間上升（修正前的節點，每筆寫入的成本與 log 長度成正比）。
拿掉它，延遲的上升可能一半來自節點、一半來自工具，就分不出來了。有了它，修正前「直接送出」那一列是平的，證明這個節點在這個設定下沒有成長的成本。

**2.** 排除了「節點變了」的可能。兩列唯一的差別是送出的方式，所以兩列之間的差距只能來自工具。

**3.** 每次請求是 O(n)：第 n 次要序列化並寫出 n 筆。整個量測是 O(n²)：3,000 次請求總共寫出約 3,000 × 3,000 / 2 筆紀錄。

**4.** 因為測試判斷對錯用的是記憶體中的 `c.history`，寫出的檔案只是給人除錯看的。工具變慢不會讓任何斷言失敗，只會讓測試跑得久一點，以及讓量測數字變得不可信。

**練習：實際執行結果（2026-11-15）**

```text
500 entries: 3.9 ms per rewrite, 0.61 MiB
1500 entries: 10.6 ms per rewrite, 1.83 MiB
3000 entries: 12.1 ms per rewrite, 3.67 MiB
```

（每個大小重寫 20 次取平均，寫到 session 的暫存目錄。）3,000 筆時一次重寫約 12 ms，和第 3 節修正前兩列在最後 500 筆的差距（18.1 − 4.6 ≈ 13.5 ms）是同一個量級。
差距略大於單獨重寫的時間；`repro.sh` 只有一個用戶端依序送出，沒有鎖的爭用，多出的部分推論是同一次呼叫裡 Python 的其他工作（例如字典複製），沒有另外量測。
