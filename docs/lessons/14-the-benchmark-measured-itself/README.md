# 量測工具量到的是它自己：每次請求都重寫整份歷史檔

狀態：草稿

> 這篇的命令與輸出都實際執行過（2026-11-15），還沒有第二個人照著做一遍。
> 讀者設定：會用 Python 呼叫函式；知道本專案用 `tools/cluster.py` 啟動測試叢集即可。

發現日期：2026-11-15　｜　發現方式：S5 實作時改寫量測工具，前後數字對不起來　｜
影響的版本：V1 起的 `tools/cluster.py`（`Cluster.invoke`）　｜　修正：commit `dd1565f`

## 1. 一句話說後果

S5 的規格說「資料越多，寫入越慢，而且有一個來源不明的成本」。其實那個成本有一部分是**量測工具自己**：每送一個請求，工具就把到目前為止的整份歷史重寫進磁碟。

這篇帶你用一個命令看到：同一個節點程式、同一批寫入，只換送出的方式，延遲曲線就從「一路上升」變成「一條水平線」。

## 2. 需要的背景

**`Cluster.invoke`。** 測試用的叢集工具提供 `invoke(payload)`：送出一個請求，並把「何時送出、何時收到、結果是什麼」記進 `self.history`。
線性一致性檢查器之後會讀這份歷史，判斷系統的行為是否正確。

**量測的基本要求。** 量「節點處理一筆寫入要多久」時，碼表裡只應該有節點的工作。碼表裡多了別的東西，而那個東西又會隨時間變化，量到的趨勢就不能歸給節點。

**一個成本的成長方式。** 若每次請求要做的事和「之前做過幾次」成正比，第 n 次就要花 n 份時間；總共做 N 次，總成本約是 N² / 2。這種成本一開始不明顯，越後面越重。

## 3. 親手重現

需要 Linux 或 WSL、Rust、Git，以及專案的 `.venv`。在專案根目錄執行：

```bash
docs/lessons/14-the-benchmark-measured-itself/repro.sh
```

約 2～3 分鐘。它在 `artifacts/runs/` 底下建暫存目錄（ext4，fsync 的成本是真的），結束時刪除。完整輸出在 [expected-output.txt](expected-output.txt)。

腳本從 tag `s1-s4-review-verified` 建出節點程式，用 `--snapshot-every 64` 讓 log 一直很短（這樣節點自己的每筆成本不可能隨時間上升），
各寫 3,000 筆 1 KiB 的值，每 500 筆記一次延遲的中位數：

```text
== before the fix: s1-s4-review-verified node and its tools/cluster.py; 3000 writes of 1 KiB, log kept short
   Cluster.invoke  p50 ms per 500 writes:   6.7   9.7  11.6  14.1  16.8  18.1   history.json 3.7 MiB
   kv_client.call  p50 ms per 500 writes:   4.7   4.6   4.6   4.5   4.7   4.6   history.json 0.0 MiB

== after the fix: the same node, the current tools/cluster.py
   Cluster.invoke  p50 ms per 500 writes:   4.5   4.6   4.6   4.5   4.6   4.6   history.json 0.0 MiB
```

同一個節點程式：經舊工具送出時延遲從 6.7 ms 一路漲到 18.1 ms；直接送出時一直是 4.6 ms 左右。
（修正後那一列的 `history.json 0.0 MiB` 是因為檔案改在叢集關閉時才寫，量的時候還不存在。）

## 4. 為什麼會這樣

修正前的 `Cluster.invoke`：

```python
with self.history_lock:
    self.history.append({...})
    (self.directory/"history.json").write_text(json.dumps(self.history,indent=2))
```

每次呼叫都把**整份**歷史序列化並寫進檔案。每筆紀錄帶著 1 KiB 的值，3,000 筆後檔案是 3.7 MiB。練習中實測，單是寫一次 3,000 筆的歷史就要約 12 ms——比節點處理那筆寫入還久。

```mermaid
flowchart LR
    T0["碼表開始"] --> S["送出請求"] --> N["節點處理：約 4.6 ms，固定"] --> R["收到回覆"]
    R --> H["重寫整份 history.json：隨請求數成長"] --> T1["碼表結束"]
```

這個寫檔不在節點裡，卻在碼表裡。S5 的基準量測（規格 §2 的表 A、表 B）就是用 `Cluster.invoke` 送請求的，所以：

- 表 B「快照之後 log 只有 294 筆，延遲卻有 21 ms」那個「來源不明的成本」，大部分是這份越來越大的歷史檔。
- 表 A 的 32 個用戶端也受影響：每個請求都要搶同一把鎖、寫同一個檔，量到的並行度被工具壓低。

## 5. 為什麼嚴重

- **它不影響系統的正確性**：節點沒有錯，測試的判斷（線性一致性）也沒有錯，因為檢查器讀的是記憶體中的歷史。
- **它讓效能結論錯了方向。** 規格因此把「找出隨資料量成長的第二個成本」列為第一步，差點去改節點裡根本不存在的問題。
  若沒發現，S5 的「前後對照」也會把工具的成本算進「改善前」，誇大改善幅度。
- **它從 V1 就存在**：之前的 benchmark（`tools/benchmark.py`）也經過 `Cluster.invoke`，數字都包含這個成本；那時請求數少、值很小，所以不明顯。

## 6. 怎麼修

歷史只在記憶體中累積，叢集關閉時寫一次檔案（`Cluster.save_history`，由 `close()` 呼叫）。
新的量測工具 `scripts/write_benchmark.py` 另外改用 `kv_client.call` 直接送出，碼表裡只有請求本身。

| 其他做法 | 為什麼沒選 |
|---|---|
| 每次只附加一行到檔案（JSON Lines） | 可行，但歷史檔是給人看與除錯用的，測試從不在中途讀它；只在關閉時寫最簡單 |
| 量測時改用別的工具，不動 `Cluster.invoke` | 所有整合測試都經過它；越長的測試越慢，修掉對大家都有好處 |

## 7. 怎麼證明修好了

- 第 3 節的對照：修正後，同一個節點經 `Cluster.invoke` 的延遲與直接送出相同，且不再隨請求數上升。
- 全部整合測試照常通過：它們讀的是 `c.history`（記憶體），沒有一個依賴中途寫出的檔案。
- 首次發現的紀錄：2026-11-15 實作 S5 時，新的量測工具（直接送出）量到修正前的節點在 log 很短時沒有額外成本，與規格的表 B 不符；之後以 `repro.sh` 的對照確認。

## 8. 還沒解決的事

- 規格 §2 的表 A、表 B 是用舊工具量的，數字保留原樣作為紀錄；S5 的正式前後對照以 `write-benchmark.json`（直接送出）為準，補記中寫明。
- 測試中途若程式崩潰而沒有走到 `close()`，歷史檔就不會寫出；`with Cluster(...)` 的寫法會走到，手動建立的叢集要自己呼叫 `close()`。
- V1 時期 `artifacts/reports/benchmark.json` 的數字包含這個成本，沒有重量。

## 9. 自我檢查與練習

解答在 [answers.md](answers.md)。

1. 為什麼 `repro.sh` 要用 `--snapshot-every 64`？拿掉它會讓結論變得不可靠嗎？
2. 第 3 節修正前的兩列用的是同一個節點程式，這個安排排除了什麼可能？
3. 這個成本是 O(n) 還是 O(n²)？是指每次請求，還是整個量測？
4. 為什麼這個問題沒有讓任何測試失敗？

**動手練習：一次重寫要多久？**

- 起點：用 Python 建一個 n 筆的歷史清單，每筆帶 1 KiB 的值，`json.dumps(..., indent=2)` 後 `write_text`。
- 目標：量 n = 500、1,500、3,000 時重寫一次的時間，和第 3 節的延遲差距比較。
- 怎麼知道做對了：你的數字能解釋第 3 節兩列的差距大致從哪裡來；和解答的實測比對。

## 10. 面試時怎麼講

**兩分鐘版本**

- **情境**：我在做 Raft KV store 的效能優化，先量基準。數據顯示寫入延遲隨資料量上升，其中一部分我在節點裡找不到原因。
- **怎麼發現**：我寫了新的量測工具，直接送請求、不經測試框架，結果同一個舊版節點在 log 很短時延遲是平的，和舊數據不符。
- **根因**：測試框架的 `invoke` 每次呼叫都把整份歷史序列化寫檔，成本隨請求數成長，而它就在碼表裡。
- **修法與取捨**：歷史只在結束時寫一次；量測工具直接送請求。沒有改成逐行附加，因為沒有人在中途讀它。
- **怎麼驗證**：同一個節點、同一批寫入，只換送出方式：舊工具 6.7→18.1 ms，直接送出 4.6 ms 持平；修正後兩者相同。
- **學到什麼**：量效能之前，先確認碼表裡只有你要量的東西；一個「找不到原因的成本」，值得先懷疑量測工具。

**可能的追問**

- *「你怎麼確定不是節點的問題？」* 讓節點的 log 一直很短，並用同一個二進位檔做兩種送法；只有工具不同，差距就只能來自工具。
- *「之前的數字還能用嗎？」* 保留作為紀錄，但正式的前後對照用新工具重量；文件裡寫明哪些數字受影響。
- *「怎麼避免下次再發生？」* 量測工具與測試框架分開，量測只用最薄的客戶端；並在報告裡寫明碼表包含哪些步驟。
