# 開發歷程

這份文件說明專案分幾個階段做、每個階段加了什麼、刻意不做什麼，以及每次審查找到了什麼。
進度以 Git tag 為準：名稱以 `-verified` 結尾的 tag，只在那個階段的驗收全部通過後才建立。（`s7-`、`s8-` 開頭的三個 tag 屬於另一項研究，見下方。）

## 目的與由此而來的取捨

這個專案是為了學習分散式共識，以及在面試時展示。因此：

- **只維護一個最後版本。** 儲存格式改版時不做新舊並存與遷移工具；舊版留在 Git tag，需要重現舊 bug 時從 tag 取出。
- **每個遇到的 bug 都寫成教學。** 有可以執行的重現、當時的輸出、修正前後的程式（[bug 教學](lessons/README.md)）。
- **功能和驗證衝突時，以驗證為準。** 達不到驗收標準的功能，寧可刪掉或寫明驗到哪裡，也不以「可用」的名義留著。

## 每個階段的固定流程

規格（包含「不保證的事」）→ 核准 → 先寫會失敗的測試 → 實作 → 模擬與故障測試 → 獨立審查 → 寫教學 → 跑驗收 → 本機 commit 與 tag。

驗收由 `scripts/verify_gate.py` 依 `acceptance/final.json` 執行。加了功能或修補的開發階段（S1～S6 與 S10）在契約裡各加一個驗收階段；
後面的驗收階段會連同前面所有階段的測試一起跑，所以新功能不能讓舊的保證退步。

## 為什麼是這個順序

順序由相依關係決定：

- 壓縮要刪掉舊的 log，前提是儲存格式可信，所以 S1 在 S2 之前。
- 新節點加入時要靠快照才追得上，所以 S2 在 S4 之前。
- ReadIndex 和成員變更都要知道「現在的成員是誰、多數是幾台」；S3 把多數的計算集中到一處，S4 再改成依成員設定計算。
- 效能最後做，才有穩定的基準可以比較；而且效能最佳化不能改變「先落盤、後回覆」的次序。

S2 是影響最大的一次重構：程式原本到處假設「log 的第幾個位置就是第幾個 index」，壓縮之後 log 有了起始位移，每一處都要改。

## 刻意不做的事

| 不做 | 為什麼 |
|---|---|
| joint consensus（一次改多台） | 一次一台已經能完成所有成員變更，規則也少得多 |
| lease read | 依賴時鐘的假設；ReadIndex 不需要 |
| leader transfer、learner（不投票的追趕節點）、PreVote | 不是其他功能的正確性所必需；追趕改由 leader 在加入前先做（S4） |
| 新舊儲存格式並存、遷移工具 | 只維護一個最後版本 |
| 形式化證明 | 超出範圍；改用模擬器的不變量、故障注入、mutation 測試與獨立審查 |

## 2026-11-15 的計畫縮減

專案花的時間比預期長，作者決定縮小範圍，只做重點功能和能完成的驗證。原本計畫的三項驗證因此沒有做，README 照實列在「沒有驗證的事」：

- 長時間的浸泡測試，以及大量操作的故障注入下的線性一致性檢查（現在一次最多檢查 24 個操作）。
- 修補模擬器的盲點：管理者一次只送一個成員變更，每個種子只有 64 個用戶端操作。
- 由第三位審查者再看一次 S1（S1 的審查者也參與過 S1 的撰寫）。

## S10：最後一次複查

這次不加功能，只問一件事：程式和文件現在說的是不是真的。做法是重跑所有以前「做過一次就沒再跑」的東西，再請沒參與實作的審查者讀儲存層。

| 找到的問題 | 怎麼發現 | 處理 |
|---|---|---|
| 只有一台 voter 時，GET 一定逾時 | 讀讀取的路徑時問「沒有 follower 時誰會呼叫回答讀取的函式」 | 修正；[教學 20](lessons/20-a-leader-alone-never-answers-reads/README.md) |
| 全新 clone 第一次 `cargo test` 有 3 個測試失敗；同時啟動的節點可能起不來 | 執行 `scripts/clean_rebuild.py`（在新目錄從頭建置、跑全部測試） | 修正；[教學 21](lessons/21-a-fresh-clone-fails-its-first-test-run/README.md) |
| log index 接近 u64 上限時，驗證全部放行，之後溢位 | 儲存層審查 | 新增 `MAX_LOG_INDEX`，五處驗證都檢查 |
| 16 段檢查可以整段刪掉而沒有測試失敗 | 審查者在 30 個地方植入錯誤，各自只跑相關套件的測試 | 12 段補了測試，並登記成 mutation 案例；另外 4 段（`Envelope::valid_for` 裡重複的 voters 檢查、來自自己的訊息、長度為 0 的 frame、快照檔的大小上限）別處已再檢查一次或影響很小，當時沒有補；S12 補上（見下一節） |
| `HANDS_ON.md` 的一鍵示範從 S5 起就跑不完 | 照文件實際執行 | 修正，並加一個跑完整個示範的測試 |
| 教學 06、13 的重現腳本從 S4、S5 起就失效 | 重跑全部 21 篇的重現 | 改成從固定的 tag 取程式；新增 `scripts/run_lesson_repros.sh` |
| 帶讀文件還停在 V1（「始終三節點」「重啟後 commit index 是 0」） | 對照目前的程式重讀 | 重寫 [帶讀](LEARNING_GUIDE.md) 與 [實際操作](HANDS_ON.md) |

S5 審查留下一個「無法解釋的失敗」：某個 mutant 執行時，一個和它無關的測試失敗了 4 次，之後再也沒有重現。
這次把那個測試以 16 個並行跑了 400 次，沒有失敗。最可能的原因是當時的副本放在 4.3 GB 的 tmpfs 上、同時有其他建置在跑，空間不夠導致寫檔失敗；
但當時的執行器沒有保存輸出，這個推論無法證實，所以列為未解。

從這次學到的事：**做過一次的檢查不會自己保持正確。** 示範腳本、教學的重現、乾淨環境的重建，都在某個階段之後悄悄壞掉，
因為它們不在每次都跑的驗收裡。這次把示範加進測試，把教學的重現做成一支可以重跑的腳本。

## S12：補上最後 4 段檢查的測試

S10 的審查留下 4 段「整段刪掉也沒有測試失敗」的檢查。當時判斷它們別處已經再檢查一次，或影響很小，所以沒有補。
這次把它們補上，S10 審查找到的 16 段檢查現在都有測試把關。不加功能，也沒有改任何一段檢查本身。

| 檢查 | 在哪裡 | 拿掉它會怎樣 | 新的測試 |
|---|---|---|---|
| 訊息不能來自收件的節點自己 | `Envelope::valid_for`（raft-protocol） | core 收到後還會再擋一次，所以原本沒有測試失敗 | `messages_from_the_receiver_itself_or_with_invalid_voters_are_refused` |
| 快照的 voters 必須是合法的成員組合 | 同上 | core 會再用 `Snapshot::valid` 檢查一次 | 同上 |
| frame 長度不能是 0 | `read_payload`（raft-transport） | 空的內容會交給呼叫者，等到解析 JSON 時才失敗 | `a_zero_length_frame_is_refused` |
| 快照檔不能超過大小上限 | `read_snapshot`（raft-storage） | 太大的檔案會整個讀進記憶體，之後才因為別的原因被拒絕 | `a_snapshot_file_over_the_size_limit_is_refused_before_reading` |

每個測試在現在的程式上通過，把對應的檢查拿掉後就失敗。這 4 種拿掉的方式登記成 `s12_*` mutation 案例，總數從 78 個變成 82 個。
驗收契約加了階段 17，列出這 3 個測試（第一個測試同時檢查前兩段）。

快照檔的測試用稀疏檔（sparse file）：把檔案大小設成上限再多 1 byte，但不寫入任何資料，所以幾乎不占磁碟空間。

## S16：持續整合

這個儲存庫公開之後，加上 GitHub Actions 的持續整合（CI）：每次 push 到 main、每個 pull request，都在一台乾淨的 Linux 機器上照 `scripts/clean_rebuild.py` 的步驟跑一遍。步驟是格式檢查、clippy、Rust 測試、建置 Python 測試要啟動的執行檔、Python 測試，最後是 client CLI 與當機重啟的示範。結果顯示在 README 最上面的徽章。

CI 不跑 1,000 個種子的模擬、兩個效能量測和 82 個 mutation 案例：這些合起來要四十多分鐘，留在完整驗收（`bash scripts/final_acceptance.sh`），每次打代表通過的 tag 前都要跑。

CI 和乾淨重建如果各改各的，兩邊說的就不再是同一件事。`tests/test_ci_workflow.py` 比對兩者執行的命令，任何一邊少了一步，這個測試就失敗；驗收契約的階段 18 列出這個測試。Rust 的版本由 `rust-toolchain.toml` 決定，workflow 不另外寫一份。
