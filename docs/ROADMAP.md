## 專案目的與由此而來的取捨

目的是**學習**與**面試時展示能力**，並藉開發過程改進使用者自己的 AI 框架。因此：

- 只做一個「最後一版」：不維護新舊格式並存，不做遷移工具與 rollback。舊版以 Git tag 保存，
  需要重現舊 bug 時切回 tag。
- 程式由 AI 完成；每個階段附新手導向的教學與練習，讓使用者事後能跟著做一遍並講給別人聽。
- 開發中遇到的每個 bug 都寫成教學文件（見「Bug 教學」）。
- 功能之間若有衝突或無法達到驗收標準，AI 可自行修改設計或刪減，但必須寫明刪了什麼、為什麼。
- 最後整理成可公開的 GitHub 儲存庫，README 與架構總覽中英並列，教學維持繁體中文。push 由使用者執行。

不變的底線：三份原始規格保留原文；不削弱測試來換取通過；分清楚「已執行通過」「推論」「未驗證」；
不宣稱 production-ready 或形式化證明；相鄰的 ai-general-framework 唯讀。

### S7、S8 的依據（使用者 2026-11-15 提供，原文照錄）

**中文文件的「AI 味」**：

- 掉入「流暢性陷阱」：語意空洞的精美廢話
- 歐化中文與「倒裝長句」的大量堆疊
- 缺乏「主題鏈（Topic Chain）」與人稱跳躍
- 資訊密度過高與「名詞化（Nominalization）」
- 死物配活物動作
- 沒見過的詞語搭配
- 主詞和動詞離太遠

使用者給的參考論文（兩篇都只研究英文，中文的部分要自己定義；以下摘要取自網頁讀取代理的報告，S7 引用前要回原文核對）：

- arXiv 2610.29162，Clark、Martin、Mahowald，〈Why is AI-generated language so hard to understand?〉：LLM 比人更常用「無生命的主詞配有生命的動詞」、
  語料中罕見或沒出現過的詞語組合、距離很遠的依存關係、堆疊的名詞複合詞與省略關係代名詞的子句；作者推測來自後訓練追求資訊密度的壓力。
- arXiv 2610.23715，Cekini 等，〈The Cognitive Cost of LLM Writing〉：LLM 改寫後的文字較短，但每個字的預估閱讀時間較長，用字較長、較少見，詞彙多樣性較高。

**好的 AI 框架應該做到**：

- SKILLS、SCRIPTS、REFERENCE、MCP、CI 沒有重疊、衝突、誤觸、沒觸發、多餘無用等現象
- 能自然的利用多種 AI 模型，以及跨部門合作來開發（要懂得寫交接文件（跨 SESSIONS、跨模型），和紀錄重要的長期記憶）
- 個人化（像是如何視覺化 trace code，和避免文檔有 AI 味，git commit 要表達出當時為何修改，以及台灣繁體中文的語句上下文要通順自然，如何有效表達和教人）
- 降低 token 消耗（像是：類似 snippet 概念的 scripts）
- 降低 bugs 出現
- 有效率 debug，找出 root cause
- Grill me，和我對齊想法
- 能提醒開發者，還缺少啥？或是誤解了啥？
- 不會過度思考
- 不會代碼膨脹
- 有明確邊界（像是：資安隱私、CI/CD、hooks、腳本、容器等等）

### 預先聲明的刪減方案

「沒有 bug」無法保證；能做到的是：每項功能都通過模擬器的不變量檢查、故障注入下的線性一致性檢查、
mutation 測試與獨立審查，並把沒驗到的部分寫清楚。達不到這個標準的功能不會以「可用」的名義留在最終版：

- Membership change：原訂若過不了 S6 就移除。2026-11-15 起 S6 不再做那些檢查，membership 依 S4 的驗收和
  S1～S4 的審查結果保留，README 寫明它驗到哪裡。
- 不做：joint consensus（一次改多台）、lease read、leader transfer、learner（不投票的追趕節點）、
  PreVote。其中若有哪一項被證明是其他功能正確性所必需，會在該階段提出並說明。
- 效能優化若與安全性檢查衝突，以安全性為準，保留 benchmark 數字與原因。

## Bug 教學

位置 `docs/lessons/NN-簡短名稱/`，每個 bug 一個資料夾。讀者設定為**沒寫過分散式系統的新手**。固定章節：

1. 一句話說明這個 bug 會造成什麼後果。
2. 需要的背景知識（用白話解釋每個術語，第一次出現時附原文）。
3. 親手重現：可直接執行的命令、預期看到的輸出、每一步在做什麼。
4. 為什麼會這樣：沿著程式一步步追，附流程圖或時序圖。
5. 為什麼這很嚴重：對應到 Raft 的哪一條安全性質。
6. 怎麼修、考慮過哪些做法、為什麼選這個。
7. 怎麼證明修好了：哪些測試、各自擋住什麼。
8. 還有什麼沒解決。
9. 自我檢查題與一個動手練習（附解答位置）。
10. 面試時怎麼講：兩分鐘版本的重點。

第一篇是已重現的 WAL 長度欄位毀損。工程強化階段找到的九個問題（見 `ENGINEERING_HARDENING.md`）
在 S0 評估哪些有足夠的保存證據可以補寫。教學中的每個命令都要實際跑過，輸出取自實際結果。

## 建議的模型分工
