# 框架經驗紀錄（ai-general-framework 在本專案的實際使用）

用途：在開發本專案的過程中，**當下**記下使用相鄰 `ai-general-framework` 的實際經驗，
作為日後改進框架的原始材料。這裡只放觀察；整理後的改進候選放
[框架改進建議](FRAMEWORK_IMPROVEMENT_PROPOSALS.md)，較早的回饋見 [FRAMEWORK_FEEDBACK.md](FRAMEWORK_FEEDBACK.md)。
本檔不代表已授權修改框架。

## 怎麼記

- 只往後追加，不改寫舊條目；後來發現有誤，新增一條註明更正哪一條。
- 順利的經驗也要記（否則只會累積抱怨，無法判斷哪些設計該保留）。
- 每條寫明：
  - **情境**：當時在做什麼、宿主與模型、框架版本（HEAD 與工作樹是否乾淨）。
  - **發生了什麼**：實際命令、輸出或檔案位置；沒有證據就寫「僅印象」。
  - **分類**：`已證實`（有可重現證據）／`觀察`（單次、未重現）／`假說`（有機制解釋但未驗證）。
  - **歸因**：框架文件、skill、helper、宿主、使用者環境、目標專案，或無法區分。
  - **對框架的可能啟示**：可空白。不要把單次觀察寫成結論。
- 不記錄憑證、私人資料；token 與費用只記宿主實際提供的數字，沒有就寫未知。

共同背景（2026-11-12 的條目皆適用）：宿主 Claude Code 桌面版，模型 claude-fable-5-2；
框架 HEAD `2569a91`、VERSION 0.2.0、工作樹有 10 個未提交修改（非本專案所為，前後數量一致）。
session 的起始工作目錄是 `/home/user/src`，不是本專案根目錄。

### L20 第一次透過宿主實際呼叫框架 skill：`review-change`
- **發生了什麼**：以 Skill 工具呼叫 `review-change` 審查 S1 的變更，宿主載入成功（L16 之後）。
  skill 要求「能指出觸發條件、執行路徑與具體後果」「必要時做有針對性的重現」，促使我實際檢查而非憑讀程式下結論：
  用 `cargo test -- --list` 確認契約內 39 個測試名稱在 workspace 中唯一；算出練習解答中長度 168（`0xa8`）的位元，
  發現原本「翻轉讓長度加 1 到 128」的說法對已設定的 bit 不成立。結果：程式碼無可證實缺陷，兩項文件問題已修正。

  **不等於獨立審查**。路線圖要求的「不同模型、新 session、不給預期答案」的審查仍待使用者另外執行。
