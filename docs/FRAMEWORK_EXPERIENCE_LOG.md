# 框架經驗紀錄（ai-general-framework 在本專案的實際使用）

用途：在開發本專案的過程中，**當下**記下使用相鄰 `ai-general-framework` 的實際經驗，
作為日後改進框架的原始材料。這裡只放觀察；整理後的改進候選放
[框架改進建議](FRAMEWORK_IMPROVEMENT_PROPOSALS.md)，較早的回饋見 [FRAMEWORK_FEEDBACK.md](FRAMEWORK_FEEDBACK.md)。
本檔不代表已授權修改框架。

## 怎麼記

- 只往後追加，不改寫舊條目；後來發現有誤，新增一條註明更正哪一條。
- 順利的經驗也要記（否則只會累積抱怨，無法判斷哪些設計該保留）。
- 每條寫明：
  - **情境**：當時在做什麼、宿主與模型、框架版本（HEAD 與工作樹是否乾淨）。
  - **發生了什麼**：實際命令、輸出或檔案位置；沒有證據就寫「僅印象」。
  - **分類**：`已證實`（有可重現證據）／`觀察`（單次、未重現）／`假說`（有機制解釋但未驗證）。
  - **歸因**：框架文件、skill、helper、宿主、使用者環境、目標專案，或無法區分。
  - **對框架的可能啟示**：可空白。不要把單次觀察寫成結論。
- 不記錄憑證、私人資料；token 與費用只記宿主實際提供的數字，沒有就寫未知。

共同背景（2026-11-12 的條目皆適用）：宿主 Claude Code 桌面版，模型 claude-fable-5-2；
框架 HEAD `2569a91`、VERSION 0.2.0、工作樹有 10 個未提交修改（非本專案所為，前後數量一致）。
session 的起始工作目錄是 `/home/user/src`，不是本專案根目錄。

## 2026-11-12

### L01 skills 只配置給 codex，Claude Code 看不到
- **發生了什麼**：`.agf/manifest.json` 的 `hosts` 只有 `codex`，專案有 `.agents/skills/`、
  沒有 `.claude/`。本 session 宿主列出的可用 skills 不含那五個。
- **分類**：已證實（單一 session）。**歸因**：部署設定與宿主的探索路徑；不是 skill 內容的問題。
- **啟示**：交接文件正確地沒有宣稱「Claude 已載入」，但也沒指出補救只要一個命令。
  換宿主的交接指引或可提一句「先跑 `project plan --host <新宿主>` 看差異」。

### L02 用框架自己的命令補上 Claude 宿主：順利
- **發生了什麼**：`project plan --target . --host codex --host claude`（唯讀預覽）顯示
  新增 12 檔、保留 17 檔、無 drift 無衝突，並提示既有 `CLAUDE.md`／`AGENTS.md` 不改寫。
  加 `--apply` 後 `project status` 為 clean、29 個受管檔案；`diff -r .agents/skills .claude/skills` 無差異。
- **分類**：已證實。**歸因**：框架 helper。
- **啟示**：「先預覽、再套用、保留既有規則檔」的流程在這次符合預期，值得保留。

### L03 配置成功後，本 session 仍無法呼叫 skill
- **發生了什麼**：套用後立刻以宿主的 Skill 工具呼叫 `review-change`，回覆 `Unknown skill`。
- **分類**：觀察。**歸因**：無法區分——可能是宿主只在 session 開始時掃描，也可能是因為
  起始工作目錄不在專案根目錄。**尚未驗證**在專案根目錄開新 session 是否會載入。
- **啟示**：再次印證「配置成功」「宿主發現」「任務中有效」是三件事。下一個 session 開始時
  請先看可用 skills 清單並補記結果（L03 的後續）。

### L04 `--root` 與 `--target` 旗標不一致造成一次失敗呼叫
- **發生了什麼**：專案規則與交接文件示範 `profile show --root <專案>`；我照同樣寫法執行
  `project status --root ...`，得到 `error: the following arguments are required: --target`。
- **分類**：已證實（可重現）。**歸因**：框架 CLI 介面。
- **啟示**：同一個「目標專案目錄」在不同子命令用不同旗標名稱。可考慮統一或互設別名；
  影響小，但每個新接手的代理都可能踩一次。

### L05 部署 skills 會改變本專案的來源指紋
- **發生了什麼**：本專案 `scripts/verify_gate.py` 的指紋排除 `.agf` 但不排除 `.agents`、`.claude`。
  因此我必須等 P00～P08 重跑結束（約 17 分鐘）才能套用 L02，且套用後剛取得的 receipt
  立刻又不適用於目前來源。
- **分類**：已證實。**歸因**：目標專案的驗收策略，不是框架缺陷。
- **啟示**：框架的部署說明或可提醒「受管檔案若落在目標專案的來源雜湊範圍內，更新框架會使
  既有驗證紀錄失效」。是否把宿主設定目錄排除在指紋外，是本專案待使用者決定的政策，
  不可由代理自行放寬。

### L06 在唯讀框架執行 CLI 需加 `-B`
- **發生了什麼**：為避免 Python 在框架目錄寫入 `__pycache__`，所有呼叫都用 `python3 -B`。
  框架 `git status --short` 前後皆為 10 行。未實測不加 `-B` 是否真的會留下未忽略的檔案。
- **分類**：假說（預防性作法）。**歸因**：shared 工具模式與唯讀要求的交互作用。
- **啟示**：shared 模式下若來源目錄被要求唯讀，文件示範命令或可直接帶 `-B`。

### L07 交接後沒有把舊 receipt 說成目前通過
- **發生了什麼**：接手時先跑 `status.py`，如實回報「source changed / not run」。
- **分類**：觀察。**歸因**：無法區分——交接文件、`CLAUDE.md`、框架 workflow 指引與使用者
  當次訊息都明講了這一點。
- **啟示**：要知道哪一層真正起作用，需要拿掉其中幾層的對照實驗。

### L08 命令改寫 hook 與自動權限審查互相干擾（非框架）
- **發生了什麼**：使用者環境的 RTK hook 會改寫 Bash 命令；本 session 有兩次因「hook 在審查後
  改了輸入」而未取得審查結果，須原樣重送。
- **分類**：已證實（本 session 兩次）。**歸因**：使用者環境與宿主，不是框架。
- **啟示**：框架 tools 指引已提醒要辨認 RTK 的實際元件；此條可作為「hook 改寫命令」
  副作用的一個實例。

### L09 這次沒有新增 MCP、專案專屬 skill 或 script
- **發生了什麼**：依框架 tools 指引「先辨認所缺能力」檢視：本專案是純本機 Rust／Python
  開發，建置、測試、驗收與證據保存都已有 CLI 與既有 scripts，沒有找到需要外部連線的能力缺口。
- **分類**：觀察（判斷，非實驗）。**歸因**：框架指引與代理判斷一致。
- **啟示**：若 V2 過程中出現具體缺口（例如反覆需要查外部規格），再回來補記並評估。
